# 作品说明与场景亮点

> **作品名称**：大学生知识管理与反思平台（Knowledge Reflection Platform，KRP）
> **作品版本**：v0.1.0（与 `frontend/package.json` 的 `version` 保持一致）
> **一句话定位**：将碎片笔记转化为结构化知识图谱，通过 AI 主动提问引导反思，并将个人知识体系发布为可对话的 AI 数字分身。
> **技术栈**：Vue 3 + Vite + Pinia + Element Plus + ECharts ｜ FastAPI + SQLAlchemy（异步）｜ Neo4j 5.26 ｜ SQLite / PostgreSQL ｜ Redis ｜ 华为云 MaaS

---

## 一、场景背景

### 1.1 真实痛点

大学生日常面对的是**高密度、跨学科、碎片化**的知识输入：上课记的笔记、公众号收藏、PDF 课件、B 站摘录……这些内容往往躺在不同的 App 里，形成三座"孤岛"：

1. **存了等于没存**——笔记只是文本堆砌，没有结构，复习时无从下手；
2. **只输入不消化**——缺乏"输出/自测"环节，知识点看似读过，实则没掌握；
3. **经验无法沉淀复用**——个人的知识脉络只存在于脑子里，无法总结、无法分享、无法被追问。

市面上的笔记工具（Notion、语雀、印象笔记）解决了"**存**"，却没有解决"**连**（结构化）、**问**（反思）、**用**（复用对话）"。

### 1.2 目标场景

本项目面向"**个人知识管理 + 主动学习**"这一场景，把一次知识学习的完整旅程定义为一条闭环：

```
   ┌────────┐    ┌────────┐    ┌────────┐    ┌──────────┐
   │ 上传笔记 │ →  │ 生成图谱 │ →  │ AI 反思 │ →  │ 数字分身  │
   │（原料）  │    │（结构化）│    │（内化）  │    │（对外复用）│
   └────────┘    └────────┘    └────────┘    └──────────┘
        ↑                                              │
        └──────────────  社区分享 / 克隆  ←────────────┘
```

- **输入**：上传 Markdown / PDF / TXT 笔记，系统自动抽取知识点与关系；
- **连接**：知识点组织为"书本 → 目录 → 知识点"三级树状知识图谱；
- **内化**：AI 依据掌握度主动出题、引导反思，作答后回写掌握度；
- **复用**：把知识图谱向量化，训练出"可被陌生人提问"的 AI 数字分身；
- **传播**：把知识书发布到知识广场，他人可一键克隆到自己的图谱。

### 1.3 为什么值得做

- **对个人**：把"散落的知识"变成"可复习、可自测、可对话的知识资产"，形成真正的学习正反馈；
- **对社群**：知识书可发布、可克隆，让优质知识结构在用户间流动；
- **对技术**：它是一条天然的"AI 原生应用"链路，把 LLM 抽取、向量检索（RAG）、推荐式提问、实时流式对话等能力串成可演示的完整闭环。

## 二、功能架构

### 2.1 总体功能架构

系统自上而下分为四层，职责单一、依赖收敛：

| 层次 | 组成 | 职责 |
|------|------|------|
| **表现层** | Vue 3 SPA（11 个页面 + 全局悬浮宠物） | 页面交互、图谱可视化、流式对话体验 |
| **接口层** | FastAPI `api/v1/endpoints`（8 个模块） | RESTful API + WebSocket，统一挂载 `/api/v1` |
| **领域层** | `services`（9 个领域服务）+ `ai_service`（含 `providers` 抽象层） | 抽取、图谱、反思、分身、宠物、通知等业务编排 |
| **数据层** | SQLAlchemy 模型（7 个）+ Neo4j + Redis | 关系数据、图数据与向量、缓存三库协同 |

### 2.2 后端功能模块

**8 个 API 端点模块**（`backend/app/api/v1/endpoints/`）：

| 模块 | 职责 |
|------|------|
| `auth` | 注册 / 登录 / 短信验证码 / JWT 签发 |
| `notes` | 笔记上传、解析、列表、删除、重新抽取 |
| `graph` | 知识图谱节点 / 关系 CRUD、知识书查询、快照 |
| `reflection` | 反思问题生成、作答评分、掌握度回写 |
| `avatar` | 数字分身配置、知识范围、头像上传 |
| `community` | 知识广场发布 / 列表 / 点赞 / 克隆 / 封面上传 |
| `notifications` | 消息通知 |
| `pet` | 宠物状态、聊天（SSE 流式）、成长与收割 |

**9 个领域服务**（`backend/app/services/`）：

`file_parser`（多格式解析）· `ocr_service`（图片 OCR）· `extraction_service`（LLM 知识抽取）· `graph_service`（Neo4j 读写）· `reflection_service`（问题与评分）· `avatar_service`（分身配置）· `pet_service`（游戏化）· `notification_service`（通知）· `ai_service`（LLM / Embedding 统一适配，底层 `providers`）

**7 个数据模型**：`user` · `note` · `avatar` · `reflection` · `community` · `notification` · `pet`。

### 2.3 前端功能页面

`frontend/src/views/` 共 **11 个页面**：

| 页面 | 功能 |
|------|------|
| `Dashboard` | 首页：认知之树 + 宠物家园 + 成就星图 |
| `Notes` | 笔记管理：上传、统计卡、掌握度趋势、格式徽章 |
| `NoteCategory` | 笔记分类视图 |
| `BookDetail` | 知识书详情（目录 + 知识点） |
| `GraphViewer` | 知识书架：3D 拟物化书本 + 学科标签 + 入口动画 |
| `Reflection` | AI 反思：居中卡片流答题 |
| `Avatar` | 数字分身配置：知识范围、人格、头像 |
| `VisitorChat` | 分身访客对话：流式打字机 + 防幻觉拦截 |
| `Community` | 知识广场：Hero 搜索 + 卡片网格 + 分页 |
| `CommunityDetail` | 广场帖子详情 + 只读图谱预览 |
| `SearchResults` | 全局搜索结果 |

状态由 Pinia 管理（`stores/user.js` 登录态、`stores/demo.js` 演示模式）；全局悬浮宠物 `PetFloat`（含内嵌对话弹窗，头像由 `PetAvatar` 渲染）贯穿所有页面。

### 2.4 核心业务闭环的实现路径

```
上传笔记 ──► file_parser 解析 ──► extraction_service 调 LLM 抽取
        ──► graph_service 写入 Neo4j（书本-目录-知识点三级树）
        ──► reflection_service 生成问题 ──► 作答评分 ──► 回写掌握度
        ──► avatar_service + ai_service 向量化 ──► RAG 检索对话
        ──► community 发布/克隆 ──► pet_service 知识驱动成长
```

## 三、核心亮点

### 3.1 从"碎片笔记"到"三级树状知识图谱"

- 一次上传，AI 自动抽取知识点与关系，并组织为**书本 → 目录 → 知识点**的三级结构，而非一堆散点；
- 图谱页面提供**分栏森林布局**：每本知识书独立成列、列内垂直展开，支持双层收展（按书 / 按节点）；
- 知识图谱按"知识书"为单位组织大纲，符合"一本书一份脉络"的直觉心智。

### 3.2 AI 主动反思：把"读过"变成"掌握"

- 结合**掌握度阈值 + 间隔重复策略**，AI 每日定时（APScheduler）主动生成反思问题；
- 作答后按"**概念 / 逻辑 / 举例**"三维度加权评分，结果**回写掌握度**，驱动后续出题；
- 形成"测—评—补"的闭环，让学习进度可视化。

### 3.3 数字分身：可对话的知识资产 + 防幻觉

- 将知识图谱的知识点向量化（bge-m3，1024 维），存入 Neo4j 向量索引；
- 访客提问时做**相似度检索**（默认阈值 0.7，可配 `AVATAR_SIMILARITY_THRESHOLD`）+ **关键词兜底**双重约束，拦截知识库外的问题，降低幻觉；
- 通过 **WebSocket 流式输出**（`welcome → sources → chunk → done`），配合前端打字机效果，对话自然流畅。

### 3.4 游戏化：知识输入驱动宠物成长

- 注册即获得一只独特宠物；知识输入驱动花园树上的果实成长；
- 果实可收割、投喂，宠物随 `level` 动态切换对话人格（越养越"聪明"）；
- 把"坚持学习"这件反人性的事，包装成可感知的成长反馈。

**成长数学模型**：知识点按边际递减曲线（`growth_from_nodes`，严格凹、可逆、端点 0→100）折算为成长值；每满 `KNOWLEDGE_FOR_FULL` 个知识点结算一个完整成长轮次，`growth_cycles`（满额轮次）与 `tree_growth`（当前轮进度）构成无损状态——**一次性批量导入不丢溢出**，同一批知识也不重复结算，`harvest` 用原子条件更新杜绝并发重复收割。

**情感状态机**：宠物持有 `mood`（happy/excited/content/curious/proud/lonely/tired）、`bond` 亲密度与 `streak_days` 连续打卡；投喂/收割/对话/学习分别触发情绪跃迁，久未互动则按天衰减亲密度并转为 `lonely`/`tired`，让"被陪伴"有真实的记忆与惯性。

**多轮记忆与主动关怀**：对话历史落库（`pet_messages`），由性格 × 物种 × 情绪组合出个性化人设注入 Prompt；每日首次进入或久未互动时，宠物按情绪与时段**主动开口**问候，强化"被需要"的陪伴感。

### 3.5 工程化与性能

- **前端瘦身**：借助 `unplugin-auto-import` / `unplugin-vue-components` 实现 Element Plus 与 ECharts 按需引入，**主包由约 1296 kB 降至约 497 kB**；
- **测试基线**：pytest 建立 **234 个用例（全通过 / 5 已知 xfail）**，覆盖 API、服务与 WebSocket；
- **本地 CI**：`scripts/ci.bat` 一键跑"后端测试 + 前端构建"，提交前自检；
- **健壮性**：统一 `nodes_count` 语义、社区分页下推数据库、抽取指数退避重试、图片上传魔数校验、图片笔记经 OCR 识别后入链、SQLite naive-UTC 时间统一处理。

### 3.6 设计体系：统一的深色科技风

- 全站沉淀 **Linear Aesthetic** 设计语言：近黑背景、微边框、毛玻璃、青 `#22d3ee` / 紫 `#6366f1` 辉光；
- 沉淀为 `docs/03-前端设计规范.md`（Token / 布局 / 组件 / 页面规范）；
- 支持移动端响应式与可访问性（图标按钮 `aria-label`）。

### 4.4 一键安装脚本（`scripts/setup.bat`）

**用法**：在项目根目录执行 `scripts\setup.bat`（Windows 批处理）。脚本幂等，可重复执行。若 Python 不在默认路径，可先 `set PYTHON_CMD=<python 绝对路径>` 再运行。

**脚本自动完成**：

1. 定位 Python（`PYTHON_CMD` → `py` → `python`；Windows 上若存在经典安装路径会优先使用）与 npm，缺失时给出明确报错与退出码；
2. 在 `backend/` 下安装 `requirements.txt` 全部依赖；
3. 若 `backend\.env` 不存在，则从 `.env.example` 复制生成，并提示填写 API Key；
4. 在 `frontend/` 下执行 `npm install`；
5. 打印 Neo4j 的两种启动方式（本地 `deps/` 方式与 Docker 方式）。

脚本完整内容如下：

```bat
@echo off
setlocal

REM ============================================================
REM  KRP - one-click environment setup (Windows)
REM  1) locate Python / Node
REM  2) install backend (pip) and frontend (npm) dependencies
REM  3) create backend\.env from .env.example when missing
REM  4) print Neo4j startup hints
REM  Override the interpreter with: set PYTHON_CMD=...
REM ============================================================

set "ROOT=%~dp0.."
set "BACKEND=%ROOT%\backend"
set "FRONTEND=%ROOT%\frontend"

echo === KRP one-click setup ===

REM ---------- locate Python ----------
set "PYTHON="
if defined PYTHON_CMD set "PYTHON=%PYTHON_CMD%"
if not defined PYTHON if exist "D:\Python313\python.exe" set "PYTHON=D:\Python313\python.exe"
if not defined PYTHON (
  where py >nul 2>nul
  if not errorlevel 1 set "PYTHON=py"
)
if not defined PYTHON (
  where python >nul 2>nul
  if not errorlevel 1 set "PYTHON=python"
)
if not defined PYTHON (
  echo [ERROR] Python 3.12+ not found. Install it, or set PYTHON_CMD, then retry.
  exit /b 1
)
echo [OK] Python: %PYTHON%

REM ---------- locate Node / npm ----------
where npm >nul 2>nul
if errorlevel 1 (
  echo [ERROR] Node.js / npm not found. Install Node 18+ then retry.
  exit /b 1
)
echo [OK] npm found.

REM ---------- backend dependencies ----------
echo [1/4] Installing backend requirements ...
pushd "%BACKEND%"
"%PYTHON%" -m pip install -r requirements.txt
if errorlevel 1 (
  echo [ERROR] backend dependency installation failed.
  popd
  exit /b 1
)
popd

REM ---------- backend .env ----------
echo [2/4] Preparing backend\.env ...
if not exist "%BACKEND%\.env" (
  copy /y "%BACKEND%\.env.example" "%BACKEND%\.env" >nul
  echo [OK] created backend\.env from .env.example - fill in your API keys.
) else (
  echo [SKIP] backend\.env already exists.
)

REM ---------- frontend dependencies ----------
echo [3/4] Installing frontend dependencies ...
pushd "%FRONTEND%"
call npm install
if errorlevel 1 (
  echo [ERROR] npm install failed.
  popd
  exit /b 1
)
popd

REM ---------- Neo4j reminder ----------
echo [4/4] Neo4j is required. Start it with Docker:
echo    docker : docker compose up -d neo4j        (先在仓库根目录建 .env 并写入 NEO4J_PASSWORD)
echo    local  : 方式二需自备 JDK 21 与 Neo4j 构建产物（deps/ 未随仓库分发）

echo.
echo === setup finished ===
echo   backend : scripts\run_backend.bat
echo   frontend: cd frontend ^&^& npm run dev
endlocal
exit /b 0
```

## 五、部署运行步骤说明

### 5.1 方式一：本地开发运行（Windows，本项目当前使用）

**步骤 1 · 一键安装**

```bat
scripts\setup.bat
```

**步骤 2 · 配置 `backend\.env`**

`.env.example` 中的主机名是为 Docker 准备的（`postgres` / `neo4j` / `redis`）。**本地开发需改为 `localhost`**，并填写 AI Key：

```ini
POSTGRES_HOST=localhost
NEO4J_URI=bolt://localhost:7687
REDIS_HOST=localhost

# AI 抽取与对话：填写任一 OpenAI 兼容端点
LLM_API_KEY=<你的 API Key>
LLM_BASE_URL=<你的 Base URL>
LLM_MODEL=<模型名>

# 数字分身 RAG 所需的 Embedding 端点（bge-m3，维度 1024）
MAAS_API_KEY=<你的 Key>
MAAS_BASE_URL=<你的 Base URL>

# 图片笔记 OCR 的多模态视觉模型（可选，OpenAI 兼容）
OCR_API_KEY=<你的 Key>
OCR_BASE_URL=<你的 Base URL>
OCR_MODEL=<模型名>
```

**步骤 3 · 启动 Neo4j**（图谱与向量检索必需）

两种方式任选：

```bat
REM 推荐方式：Docker 拉起 Neo4j（仓库根目录先建 .env，写入 NEO4J_PASSWORD）
docker compose up -d neo4j

REM 若同时需要 PostgreSQL / Redis：
docker compose up -d neo4j postgres redis

REM 方式 A（作者开发机）：本地 JDK 21 + 已构建的 Neo4j
REM   注意：deps/ 未随仓库分发（已被 .gitignore 忽略），全新克隆无法使用该方式。
```

成功标志：Bolt 监听 `7687`、HTTP 控制台 `7474` 可访问。

**步骤 4 · 启动后端**

```bat
scripts\run_backend.bat
```

该脚本以 `uvicorn app.main:app --host 0.0.0.0 --port 8000` 启动，日志写入 `logs\be_out.log` / `logs\be_err.log`。

## 七、代码在项目开发中的应用总结

本作品从需求分析、架构设计到编码落地、测试与上线，形成了一套完整的工程实践。以下总结代码在其中承担的角色与应用方式。

### 7.1 总体架构与分层

- **前端**：Vue 3 单页应用，按「页面（views）— 组件（components）— 状态（stores）— 接口（api）」分层，共 11 个页面与全局悬浮宠物等组件。
- **后端**：FastAPI 分层架构，`api/v1/endpoints`（8 个业务模块，RESTful + WebSocket）→ `services`（9 个领域服务，含 2 个兼容 shim）→ `models`（SQLAlchemy 实体）/ `schemas`（Pydantic 模型），`core` 收敛配置、数据库与安全；路由统一挂载于 `/api/v1`。
- **存储**：关系数据落 SQLite/PostgreSQL，知识图谱与向量落 Neo4j，缓存走 Redis，形成「关系库 + 图库 + 缓存」的组合。

### 7.2 核心业务闭环的代码实现

围绕「笔记 → 知识图谱 → AI 反思 → 数字分身」闭环，代码实现覆盖：

1. **知识摄取**：`file_parser` 解析 Markdown/PDF/TXT，图片笔记由 `ocr_service` 经多模态模型 OCR 识别为文本 → `extraction_service` 异步调用 LLM 抽取知识点与关系 → `graph_service` 写入 Neo4j（书本-目录-知识点三级树状）；抽取过程带日志与指数退避重试，并支持「重新抽取」端点。
2. **AI 反思**：`reflection_service` 结合掌握度阈值与间隔重复策略生成问题，APScheduler 每日定时触发，作答后按「概念/逻辑/举例」加权评分并回写掌握度。
3. **数字分身**：`avatar_service` 调用 `ai_service`（底层 `providers.maas_provider`）将知识图谱向量化，基于 bge-m3 做相似度检索，配合阈值与关键词兜底防止幻觉；通过 WebSocket 流式输出对话。
4. **社区与游戏化**：社区支持发布、点赞、一键克隆知识图谱；宠物系统以知识输入驱动成长（果实成长、收割、投喂），并以等级动态切换对话人格。

### 7.3 AI 能力集成

- **提示词工程与健壮性**：LLM 调用统一由 `ai_service` 适配（底层 `providers/` 抽象层，当前实现为 `MaasProvider`，通过 OpenAI 兼容的 `/v1/chat/completions` 协议对接端点；`OpenAIProvider` 为预留空壳）；修复了历史提示词花括号未转义导致抽取从未真正跑通的问题。
- **流式交互**：对话通过 WebSocket / SSE 逐字返回（`welcome → sources → chunk → done`），前端配合打字机效果。
- **RAG 防幻觉**：检索相似度阈值（默认 0.7，可经 `AVATAR_SIMILARITY_THRESHOLD` 调整）与关键词兜底双重约束，拦截知识库外的问题。

### 7.4 前端工程化与体验

- **状态与登录拦截**：Pinia 管理用户登录态与演示模式（`stores/user.js`、`stores/demo.js`），宠物状态由全局悬浮组件 `PetFloat.vue` 本地维护；登录拦截由 axios 401 响应拦截器与菜单点击处统一触发 `LoginModal`（历史 `return false` 白屏缺陷已修复）。
- **按需引入与瘦身**：借助 unplugin 系列实现 Element Plus 与图标按需、ECharts 按需注册，主包由约 1296 kB 降至约 497 kB。
- **视觉与交互**：统一的深色科技风/毛玻璃设计体系沉淀为设计规范文档；知识图谱（知识书架 → 知识书详情）含三级目录树与思维导图收展联动、右侧抽屉；支持移动端响应式（汉堡抽屉导航）与可访问性（图标按钮 aria-label）。
- **零依赖增强**：宠物语音交互直接使用浏览器 Web Speech API，未引入额外依赖。

### 7.5 工程化实践

- **测试**：以 pytest 建立 234 个用例，覆盖 API、服务与 WebSocket；对 5 个已知的契约漂移用例标注 `xfail`，保证基线可复现。
- **本地 CI**：`scripts/ci.bat` 一键执行「后端测试 + 前端构建」，可在提交前快速自检。
- **数据演进**：无 Alembic 依赖，改用幂等的 `schema_migrations` 补列，兼容 SQLite 方言。
- **健壮性**：统一 nodes_count 语义、社区列表分页下推数据库、修复图谱删除 404、处理社区竞态与 N+1。

### 7.6 性能与安全

- **性能**：前端按需引入与代码分包；后端异步 IO、分页下推、抽取重试与日志。
- **安全**：JWT 鉴权、密码哈希、CORS 中间件、生产环境 `SECRET_KEY` 强校验、`DEBUG` 万能码仅限调试、上传文件类型白名单与魔数校验。
- **时区正确性**：针对 SQLite 时间列实为 naive UTC 的特性，业务时间统一以 `datetime.now(timezone.utc).replace(tzinfo=None)` 处理，避免 tz-aware 与库内数据混用导致的比较错误。

### 7.7 小结

代码在本作品中既是功能的承载体，也是工程方法论的落地载体：它以清晰的分层降低模块耦合，以测试与 CI 保障可复现，以性能与安全加固提升可用性，并以文档与设计规范沉淀经验，支撑「笔记 → 图谱 → 反思 → 分身」这一完整知识闭环的稳定运行。

## 八、码道（CodeArts）应用说明

> 本作品的绝大部分代码、文档与工程整理，均在**华为云码道（CodeArts）代码智能体**的协作下完成。本节总结我在真实开发中沉淀的**应用技巧、不足之处，以及如何精准便捷地使用码道**。

### 8.1 码道在项目中的实际参与方式

| 环节 | 码道承担的工作 |
|------|----------------|
| 需求梳理 | 将口语化需求整理为结构化规格，识别歧义并主动澄清 |
| 架构与设计 | 分层设计、数据模型、API 契约、前端设计规范落地 |
| 编码实现 | 后端服务 / 端点、前端页面与组件、脚本与批处理 |
| 调试排障 | 定位 bug（如表单 `.data` 多一层、token 不匹配、401 静默踢人） |
| 工程整理 | 目录归类、文档集中编号、一次性清理死文件 |
| 测试与验证 | 生成/修复单元测试、跑 `pytest`/`vite build` 客观验证 |
| 文档产出 | PRD / HLD / 作品说明 / 本说明等成体系文档 |
| 跨会话记忆 | 通过记忆文件维持约定与项目上下文，避免重复沟通 |

### 8.2 应用技巧（这些做法显著提效）

1. **给"精确锚点"而非意象描述**：用 `文件路径:行号`（如 `backend/app/services/avatar_service.py:320`）或"某函数/某 section"，比"那个页面的那个地方"高效数倍。
2. **先探查、再动手**：让码道先检索代码（explore / 语义搜索）确认现状，再改，能避免基于过时假设的错误修改。
3. **明确验收标准**：改前端说"`npm run build` 要通过"，改后端说"在 `backend/` 跑 `pytest` 不许回归"——码道会自行验证闭环。
4. **分波推进、逐波验证**：大改造拆成若干可独立验证的小步（如"先后端 → 再前端 → 最后文档"），每波跑一次校验，问题定位成本最低。
5. **刻意沉淀约定**：把"文档集中 `docs/`、按数字编号""本机 `python` 是占位程序、须用绝对路径"等约定写入记忆/`AGENTS.md`，后续会话零重复沟通。
6. **用专业 skill 加成**：UI 打磨交给 `frontend-design`、单元测试交给 `generate-ut-*` 系列，比裸提示质量更高。
7. **把"排障"也交给码道**：预设"遇阻自主穷尽方案"的偏好后，码道会自行换命令、换路径、换工具，而非轻易把问题推回给你。

### 8.3 不足之处（真实局限，使用时需知）

1. **不能直接"看"页面效果**：本环境无外网、无法自动截图，纯视觉问题（配色、间距、渲染细节）码道只能靠 `build + grep` 客观校验，**最终效果必须由你目视确认**。
2. **口语与术语存在歧义**：中文口语里的"下拉"可能指**滚动条**、"超框"可能指**文字溢出**、"没反应"可能是**视觉反馈太弱**。若不澄清，容易改错方向（这些坑在本项目中都真实踩过）。
3. **复杂视觉需多轮迭代**：认知之树、宠物弹窗等精雕类 UI 往往要 3–5 轮往返才满意，第一次很难一步到位。
4. **依赖准确的环境信息**：若未说明"必须用 `py` / `python` 启动器""pytest 必须在 `backend/` 下跑"，码道可能用错解释器/目录，导致误报。
5. **长会话上下文会漂移**：超长对话中早期约定可能被"稀释"，需依赖记忆文件兜底；会话过长时建议开新会话并指记忆。

### 8.4 如何精准便捷地使用码道

**（1）需求描述三要素**：对象 + 行为 + 验收。

```
好：把 Notes.vue 的表格列宽改自适应，改完 npm run build 通过。
差：把那个表格弄好看点。
```

**（2）先给约束，再放手**："不要动 X""保持 Y 风格""只改这一个文件"——边界越清晰，返工越少。

**（3）提供可复现入口**：账号、路径、命令、启动脚本（如登录用 `13900000001` + 万能码 `123456`、后端用 `run_backend.bat`），让码道能自己跑起来验证。

**（4）让码道"先给选项"**：多方向需求（"优化一下"）时，先要它列方案、你选定后再实施，避免它猜错。

**（5）把重复约定写进记忆**：一次性告诉它项目规矩，之后每个会话它都记得。

**（6）分阶段交付 + 及时反馈**：每完成一小块就确认一次，比"一口气全做完再验收"更稳。

**（7）信任但要复核**：码道会自行跑构建与测试，但对"视觉/体验/业务语义"这类无法自动化判定的事，仍需你把关。

### 8.5 小结

码道在本项目中扮演的不是"代码补全器"，而是一个**能主动探查、能自主验证、能跨会话记忆的工程协作伙伴**：它把"需求 → 设计 → 编码 → 测试 → 文档"的长链路串了起来，让我能把精力集中在**判断与决策**上，而非重复劳动。它的边界也很清晰——**需要眼睛看的（视觉）、需要脑子判的（业务语义）**，仍然由人来做最终裁决。用好它的关键在于：**把需求说准、把约定沉淀、把验收交给它自动跑，把审美和取舍留给自己。**

## 二、背景与架构目标

### 2.1 背景

本平台为大学生提供"笔记→知识图谱→AI 反思→数字分身"的知识闭环管理能力。详细需求见 `docs/01-需求规格说明书.md`。

### 2.2 架构目标

- **解耦**：知识抽取、图谱管理、反思引擎、分身服务各自独立，便于独立演进。
- **异步优先**：笔记解析、知识抽取、问题生成等耗时操作异步处理，保证响应速度。
- **AI 可替换**：LLM 调用通过统一接口抽象，支持切换供应商。
- **图数据原生**：充分利用 Neo4j 图查询能力支撑知识图谱与关系推理。

### 3.1 架构分层说明

| 层级 | 职责 | 技术 |
|------|------|------|
| 表现层 | UI 渲染、用户交互、图谱可视化 | Vue3 + Element Plus + ECharts |
| 接入层 | 请求路由、认证鉴权、限流、WebSocket | FastAPI |
| 业务层 | 笔记、图谱、反思、分身等核心业务逻辑 | FastAPI 路由模块 |
| AI 服务层 | LLM 调用、Embedding、知识抽取 NLP | Python（统一接口封装） |
| 数据层 | 图数据、关系数据、向量数据、缓存 | Neo4j（含向量索引） + SQLite/PostgreSQL + Redis |
| 异步层 | 耗时任务异步处理、定时调度 | FastAPI BackgroundTasks + APScheduler |

### 3.2 技术栈

| 层级 | 技术 | 说明 |
|------|------|------|
| 前端 | Vue3 + Vite + Pinia + Element Plus + ECharts + Axios | SPA，深蓝科技风毛玻璃 UI，Vite 代理 API |
| API | FastAPI + Uvicorn + Pydantic v2 | 异步框架，自动 OpenAPI 文档 |
| 认证 | JWT (HS256) + 短信验证码 | 手机号+验证码登录，无状态认证（不存密码） |
| 关系型 | SQLite（开发/单机演示）/ PostgreSQL（多实例生产） | 用户、笔记、反思、通知、分身、社区帖子 |
| 图数据库 | Neo4j (async via neo4j Python driver / AsyncGraphDatabase) | 知识节点、关系、向量索引（不可用时优雅降级） |
| 缓存 | Redis (async via redis-py) | 验证码、发送频控与登录失败计数（缺失时验证码无法下发，限流降级为进程内计数） |
| 短信 | 外部网关（`SMS_WEBHOOK_URL`，JSON POST） | 未配置时 `/auth/send-code` 明确 503；`DEBUG=true` 下可用万能码登录白名单内手机号 |
| AI | OpenAI 兼容端点（`providers/` 抽象；实际部署为通义千问 + bge-m3 Embedding） | 知识抽取、答案评估、向量检索 |
| 调度 | APScheduler | 每日反思提醒（Embedding 回填在分身发布时执行） |

## 五、核心技术选型与理由

| 技术 | 用途 | 选型理由 |
|------|------|----------|
| **Vue3** | 前端框架 | 组合式 API 适合复杂交互逻辑；生态成熟；图谱可视化库支持好 |
| **FastAPI** | 后端框架 | 原生异步高性能；自动生成 OpenAPI 文档；Python 生态无缝对接 AI/NLP 库 |
| **Neo4j** | 知识图谱存储 | 原生图数据库，Cypher 查询语言天然适合知识关系查询与路径推理 |
| **PostgreSQL** | 关系型数据 | 存储用户、笔记元数据、反思记录等结构化数据；稳定可靠 |
| **Redis** | 缓存 | 存储短信验证码与发送限流；不作为任务队列 broker |
| **Neo4j 原生向量索引** | 语义检索 | 支撑数字分身 RAG 检索；知识点 Embedding 存于节点属性，按余弦相似度匹配 |
| **APScheduler** | 定时任务 | 轻量级，Python 原生，适合反思定时提问调度；无需额外重型组件 |
| **FastAPI BackgroundTasks** | 异步任务 | 笔记解析、知识抽取等重任务异步化；无需引入独立消息队列 |
| **ECharts** | 图谱可视化 | 生态好、按需引入体积小，满足目录树与思维导图可视化 |
| **Pinia** | 前端状态管理 | Vue3 官方推荐，TypeScript 友好 |

## 六、数据流 / 调用链描述

### 6.1 笔记上传 → 知识图谱生成

```
用户上传笔记
  → notes 模块接收文件，存原始文件至本地 uploads 目录，元数据入 SQLite/PostgreSQL
  → 经 FastAPI BackgroundTasks 异步触发抽取
  → extraction 模块执行：
      1. 文本预处理（分句、清洗）
      2. 调用 ai-service：LLM 抽取知识点（名称、摘要、类型）与关系
      3. 调用 ai-service：Embedding 生成知识点向量
  → graph 模块：知识点与关系写入 Neo4j；向量写入节点 embedding 属性
  → 通知前端（WebSocket / 轮询）：图谱更新完成
  → 前端拉取图谱数据并渲染
```

### 6.2 AI 定时反思提问

```
APScheduler 定时触发（按用户设定频率/时间）
  → reflection 模块：
      1. 查询用户知识图谱（Neo4j）中掌握度低 / 即将遗忘的节点
      2. 结合间隔重复策略选取目标知识点
      3. 调用 ai-service：基于知识点生成反思问题（1-5 个）
  → notification 模块：推送站内提醒
  → 用户进入反思中心作答
  → reflection 模块：调用 ai-service 评估作答，生成反馈与掌握度评分
  → 更新 Neo4j 节点掌握度属性；反思记录入 PostgreSQL
```

### 6.3 数字分身对话（RAG）

```
访客通过分享链接发起对话（WebSocket）
  → avatar 模块接收消息
  → RAG 检索流程：
      1. 调用 ai-service：将访客问题 Embedding 化
      2. Neo4j 向量索引检索：召回 Top-K 相似知识节点
      3. Neo4j 查询：扩展召回节点的关联上下文（1-2 跳邻居）
      4. 组装上下文 + 用户分身配置（风格/范围）
  → 调用 ai-service：LLM 基于上下文流式生成回答
  → 流式返回前端，附带知识来源标注
  → 对话记录入 PostgreSQL
```

### 6.4 数据流总览

```
笔记上传 → 文本解析 → LLM知识抽取 → 节点+关系写入Neo4j
                                    ↓
                              Embedding回填 → 向量索引
                                    ↓
每日调度 → 查询薄弱节点 → LLM生成问题 → 用户答题
                                              ↓
                                    LLM评估 → 更新掌握度 → 通知
                                              ↓
                                    分身对话 → 向量检索 → RAG生成 → 流式推送
                                              ↓
                                    社区发布 → 图谱快照 → 知识广场 → 一键克隆(mastery=0)
```

## 八、关键子系统深入设计

### 8.1 RAG 防幻觉流程

```
用户提问
    │
    ▼
┌──────────────────────────────────┐
│ Step 1: 向量化查询               │
│ MaaS bge-m3 Embedding(query)    │
│ → query_embedding [1024维]       │
└──────────────┬───────────────────┘
               ▼
┌──────────────────────────────────┐
│ Step 2: 向量检索 (Neo4j)         │

      Yes  │       │  No

┌──────────────┐  ┌──────────────────┐
```

**防幻觉三道防线：**

| 防线 | 机制 | 配置参数 |
|------|------|----------|
| **第一道：向量召回** | 仅从用户自己的知识图谱中检索，不引入外部知识 | `AVATAR_TOP_K=5` |
| **第二道：相似度阈值** | 余弦相似度 < 0.7 的节点直接丢弃，避免低相关内容混入 | `AVATAR_SIMILARITY_THRESHOLD=0.7` |
| **第三道：拒答机制** | 无任何节点通过阈值时，返回 `blocked` 事件，明确告知"超出知识范围" | WebSocket `type: "blocked"` |

**关键设计：**

- **Prompt 约束**：System Prompt 明确要求"仅基于以下知识回答，不得编造"
- **来源标注**：每个回答附带 `sources` 数组，包含节点名称、学科、掌握度、来源笔记
- **知识隔离**：向量检索带 `user_id` 过滤，不同用户的知识库完全隔离

### 8.2 艾宾浩斯遗忘曲线调度算法

#### 8.2.1 理论基础

艾宾浩斯遗忘曲线描述记忆保持率随时间衰减的规律：

```
R = e^(-t/S)

其中：
  R = 记忆保持率 (0~1)
  t = 距上次复习的时间间隔（天）
  S = 记忆强度（与复习次数正相关）
```

#### 8.2.2 算法流程

```
┌─────────────────────────────────────────────────────┐
│              每日反思调度 (APScheduler)              │
│  Cron: REFLECTION_CRON_HOUR:REFLECTION_CRON_MINUTE  │
│  (默认 20:00 每日触发)                               │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│ Step 1: 查询待复习节点                               │
│ GraphService.get_nodes_for_review(                  │
│   user_id,                                          │
│   mastery_threshold=60.0,   ← 掌握度低于60%         │
│   days_threshold=7,         ← 或超过7天未复习        │
│   limit=15                  ← 先取 3 倍候选          │
│ )                                                   │
│                                                     │
│ Cypher:                                             │
│ MATCH (n:KnowledgeNode {user_id: $uid})             │
│ WHERE n.mastery < 60                                │
│    OR n.last_reviewed IS NULL                       │
│    OR duration.between(                             │
│         n.last_reviewed, datetime()).days >= 7      │
│ RETURN n ORDER BY n.mastery ASC,                    │
│              n.last_reviewed ASC                    │
│ LIMIT 15                                            │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│ Step 1.5: 弱信号重排（只改顺序，不改掌握度）          │
│ - 来自最近 3 天上传笔记的节点        +2.0           │
│ - 近 7 天被分身回答引用             +1.5/次（上限3）│
│ - 近 7 天被打开查看                 +0.5/次（上限1.5）│
│ 同分时回落到「掌握度升序」→ 取前 5 题                │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│ Step 2: LLM 生成反思问题                             │
│ AIService.generate_question(node_name, node_summary)│
│ → 针对每个薄弱节点生成个性化问题                     │
│ → 失败/返回空串时用模板题兜底（generated_by=template）│
│ → 同条记录写入出题依据 reason（掌握度/久未复习/弱信号）│
│ → 存入 reflection_records 表 (answer 待填)          │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│ Step 3: 用户答题                                     │
│ ReflectionService.evaluate_answer(                  │
│   user_id, question_id, answer, is_voice)           │
│                                                     │
│ 3a. LLM 评估答案质量 → mastery_score (0~100)        │
│ 3b. 更新节点掌握度:                                  │
│     n.mastery = new_score                           │
│     n.last_reviewed = now()                         │
│ 3c. 记录反思历史 (reflection_records 表)            │
│ 3d. 推送通知 (notifications 表)                     │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│ Step 4: 掌握度更新策略                               │
│                                                     │
│ 新掌握度 = w × 本次评分 + (1-w) × 历史掌握度        │
│   w 由时间衰减（半衰期 14 天）与当前掌握度动态决定    │
│   w ∈ [0.6, 0.85]，越久未复习 / 掌握度越低 → w 越大  │
│   改前值、改后值、本次 w 一并写回反思记录            │
│   （支撑「掌握度溯源」，见 8.2.5）                   │
│                                                     │
│ 分级:                                               │
│   < 60%  → 红色 (薄弱，优先复习)                    │
│   60-80% → 橙色 (基础，定期巩固)                    │
│   ≥ 80%  → 绿色 (熟练，降低频率)                    │
└─────────────────────────────────────────────────────┘
```

#### 8.2.3 待复习节点筛选（固定阈值）

当前实现采用**固定阈值**而非分级间隔：`GraphService.get_nodes_for_review` 选出满足以下任一条件的节点，按 `mastery` 升序、`last_reviewed` 升序取前 N（默认 5）：

| 条件 | 参数 | 说明 |
|------|------|------|
| 掌握度偏低 | `mastery_threshold=60.0` | `n.mastery < 60` |
| 从未复习 | — | `n.last_reviewed IS NULL` |
| 久未复习 | `days_threshold=7` | `last_reviewed` 距今 ≥ 7 天 |

> 掌握度分级（`MASTERY_THRESHOLDS`：WEAK=60 / STRONG=80）仅用于前端着色与提示，不参与节点筛选的阈值计算。

#### 8.2.4 出题排序：弱信号（不改掌握度）

掌握度过去只有一个输入——反思答题。不答题的图谱永远不动，反思每天会重复问同一批节点，
形成「自己证明自己」的闭环。弱信号只调整**今天先问哪几道**，绝不参与掌握度数值计算：

| 信号 | 来源 | 权重 | 说明 |
|------|------|------|------|
| 刚学过的笔记 | `notes.upload_time` ≤ 3 天 | +2.0 | 趁热复习，优先被追问 |
| 正被讨论 | `chat_messages.sources` ≤ 7 天 | +1.5/次，上限 3.0 | 分身回答引用过该节点 |
| 刚看过 | `node_views.viewed_at` ≤ 7 天 | +0.5/次，上限 1.5 | 节点详情打开埋点 |

排序键：`(-弱信号得分, mastery asc)`，取前 N 条；无任何信号时退化为原来的「掌握度升序」。
实现见 `app/services/review_signals.py`，`node_views` 由 `POST /graph/nodes/{id}/view` 写入。

#### 8.2.5 掌握度溯源（可解释性）

「这个知识点为什么是 62%」必须能当场回答，而不是一句「算法算的」。做法是**评分当场记账**，
不做事后公式回放（图谱初值与历史都可变，回放会漂移）：

- `reflection_records` 新增 `mastery_before` / `mastery_after` / `mastery_weight`；
- `GET /api/v1/reflection/nodes/{node_id}/mastery` 返回该节点历次反思的时间、三维护分、
  改前 → 改后、本次权重，以及三维权重与半衰期参数；
- 节点详情抽屉里以时间线展示，并明确标注「这里只解释反思带来的变化，抽取初值不在账上」；
- 记账字段上线前的历史记录如实标为「未留存前后值」，不做回放猜测。

#### 8.2.6 限流保护

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `REFLECTION_DAILY_LIMIT` | 5 | 每日最多生成 5 道反思题 |
| `REFLECTION_CRON_HOUR` | 20 | 调度触发小时 |
| `REFLECTION_CRON_MINUTE` | 0 | 调度触发分钟 |
| `EXTRACTION_MAX_ATTEMPTS` | 3 | 抽取失败最大重试 |
| `EXTRACTION_BACKOFF_SECONDS` | 2.0 | 重试退避间隔 |

## 十一、风险与待决事项

### 11.1 风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|----------|
| LLM 知识抽取准确率不足 | 图谱质量差，影响后续反思与分身 | 多轮抽取 + 人工校验入口；Prompt 持续调优 |
| LLM API 成本失控 | 运营成本高 | 批量任务限流；结果缓存；小模型做抽取、大模型做对话 |
| Neo4j 大规模图谱性能下降 | 图谱查询/渲染卡顿 | 节点分页加载；前端按需渲染子图；Neo4j 索引优化 |
| 数字分身被滥用（刷接口） | 成本与稳定性风险 | 访客 IP 限流；对话次数上限；异常检测 |
| APScheduler 多实例重复执行 | 反思问题重复推送 | 单实例运行调度 / 分布式锁选主 |

### 11.2 待决事项

- [已决: 向量存储] 采用 Neo4j 原生向量索引（cosine），未引入独立向量数据库。
- [已决: 异步任务方案] 采用 FastAPI BackgroundTasks + APScheduler，暂不引入 Celery。
- [已决: LLM 供应商] 通过 `providers/` 抽象层接入，当前实现为 `MaasProvider`（OpenAI 兼容协议）。
- [TBD: 对象存储方案] 当前为本地 uploads 目录存储；后续可视部署需要迁移 MinIO 或云 OSS。
- [TBD: 移动端适配策略] 响应式优先 vs 后续独立移动端，待用户反馈后决策。
